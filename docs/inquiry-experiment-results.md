# 문의번호 동시성 대조 실험·성능 측정 결과

검증일: 2026-10-14. [이슈 #139](https://github.com/redotlabs/server/issues/139).
기준 커밋: `c373b2053b7f15c684ee8ffae2ba1665e63acf2d`.

## 결론

- 원본의 기존 행 잠금은 유효했다. 기존 날짜 12,000건 모두 저장됐고, DB에서 두 번째 트랜잭션이 잠금 대기하는 것도 확인했다.
- 원본의 첫 행 생성 경합은 별도 문제였다. 신규 날짜에서 12,000건 중 111건 실패했다.
- 원본에서 조회 락만 제거한 실험용 대조군은 24,000건 중 16,491건 실패했다. DB 유니크 제약으로 저장된 번호 중복은 없었지만 정상 요청이 대거 실패했다.
- 수정본은 신규·기존 날짜 총 24,000건이 모두 성공했고 저장·응답 매핑·고유 번호 수·최종 순번이 일치했다.
- 수정본도 높은 동시성에서 DB 잠금과 연결 풀 대기가 남았다. 이번 변경은 정합성 수정이며 속도 개선을 입증한 결과가 아니다.

## 비교 대상과 회귀 테스트

| 대상 | 코드 차이 | 문의 회귀 12개 |
|---|---|---|
| original | 기준 커밋의 생성기. 테스트 날짜 고정을 위해 Clock 주입만 적용 | 9 통과 / 첫 행 동시 요청 3 실패 |
| unlocked | original에서 `@Lock(PESSIMISTIC_WRITE)`만 제거 | 4 통과 / 8 실패 |
| fixed | 안전한 초기화 INSERT + 기존 잠금 유지 | 12 통과 / 실패 0 |

비교 사본의 repository에는 수정본의 초기화 메서드 선언이 있지만 original/unlocked 생성기는 호출하지 않는다.
실제 실행한 생성기·repository 소스와 해시를 원시 결과에 포함했다. 원본/락 제거 대조군의 빨간 테스트는 의도한 반례이며 실패 로그를 보존했다.

락 제거군에서 추가로 실패한 것은 기존 행 동시 요청 3개, DB 잠금 대기 확인 1개, 마지막 번호 경쟁 1개다.
조회 후 같은 값을 읽도록 모든 요청에 인위적 sleep을 넣은 것은 아니다. 잠금 확인 테스트만 첫 트랜잭션을 latch로 유지하고
`pg_blocking_pids`로 두 번째 트랜잭션의 대기를 관측한다. 이 제어 테스트는 성능 측정에 포함하지 않았다.

일반 회귀 검증은 신규·기존 행 각각 2/10/100 요청, 잠금 해제 후 순번 42 확인, 자정 경계,
99,999번/초과 거절, 마지막 번호에 10건 경쟁 시 정확히 1건 커밋, 저장 제약 위반 시 신규 행·기존 증가 롤백을 포함한다.
최종 전체 빌드 결과는 아래 검증 기록에 기재한다.

## 실험 환경과 측정 정의

- 로컬 macOS arm64, Temurin Java 21.0.8+9, Docker 27.5.1, Docker VM 8 CPU / 약 7.65 GiB 메모리.
- PostgreSQL 16 이미지 ID와 digest는 `evidence/inquiry-20261014/machine.json`에 고정 기록. 각 변형은 별도 일회성 컨테이너 사용.
- 실제 Flyway 스키마와 Spring/JPA 문의 생성 서비스. READ COMMITTED, Hikari 최대 연결 16. 고객사 2개에 교대로 요청.
- 초기 날짜 행 없음/순번 40, 동시 작업 수 1/8/32/100, 조건별 1,000건, 각 3회: 코드당 24,000건, 총 72,000건.
- 조건별 단일 스레드 100건 워밍업 후 데이터를 초기화한다. 워밍업과 사후 SQL 검증은 측정 시간에서 제외한다.
- 정해진 수의 worker가 요청 완료 후 다음 요청을 실행하는 **closed-loop** 모델이다. 고정 도착률의 HTTP 부하가 아니다.
- 요청 지연은 서비스 호출 시작부터 트랜잭션 프록시의 반환/예외까지이며 연결 풀·DB 잠금 대기와 commit을 포함한다. HTTP·인증·네트워크는 제외한다.
- 성공 처리량은 정상 완료 수 / 해당 조건의 전체 실행 시간. 실패 요청도 지연 분포에 포함하며 성공 요청만의 p95는 summary CSV에 따로 기록했다.
- 샘플러는 별도 DB 연결을 사용한다. 약 10ms sleep + 조회 시간 간격으로 Hikari 활성·대기 연결과 PostgreSQL Lock wait 세션 수를 수집한다. 최대값은 관측값이며 정확한 누적 잠금 대기 시간이 아니다.
- DB CPU 시간은 컨테이너 cgroup v2 `usage_usec` 차이다. CPU 백분율이 아니고 컨테이너 내 모든 프로세스 사용량이며 측정 경계의 observer 준비·정리 비용도 소량 포함한다.
- 요청 title에 요청 ID를 넣고 사후 각 정상 응답의 번호가 같은 ID로 저장됐는지 확인했다. 모든 조건에서 응답 성공 수=저장 수=고유 번호 수, 최종 순번=초기 순번+저장 수를 검증했다.

## 해석과 한계

수정본의 기존 행 조건에서 동시 작업 8개 → 100개로 늘릴 때 성공 처리량 중앙값은 약 425.3 → 372.8건/s,
p95 중앙값은 약 30.9 → 1,001.5ms였다. 100개 조건에서 최대 DB 잠금 대기 15개,
풀 대기 85개를 관측했다. 각 최대값은 서로 다른 샘플일 수 있으므로 합산하지 않는다.

락 제거군의 짧은 지연을 성능 개선이라고 해석하면 안 된다. 많은 요청이 실패로 빨리 끝나며 유효한 처리 결과가 다르다.
또한 명시적인 조회 락을 제거해도 UNIQUE 검사와 UPDATE는 DB 내부에서 잠금을 사용할 수 있어 DB Lock wait 관측값이 0이 아닐 수 있다.

이 로컬 실험에서 초기화 INSERT 추가에 따른 SQL 비용은 남는다. 단일 작업 조건 등에서 수정본이 더 느린 관측도 있으므로
원본 대비 개선율이나 최대 TPS를 주장하지 않는다. 각 셀은 짧은 유한 부하이며 장시간 포화/장애/복구 시험이 아니다.

모든 변형을 같은 노트북에서 순차 실행했고 두 번째 반복은 worker 순서를 뒤집었지만 변형 순서는 original → unlocked → fixed로 고정했다.
호스트 백그라운드 부하·JIT·캐시·GC 영향을 통제하지 못했고 독립 프로세스/환경의 통계적 유의성을 평가하지 않았다.
측정 샘플링도 비용을 추가한다. 자동 재시도는 없으며 실패를 성공으로 감추지 않았다.

미실행 범위: HTTP/인증 전체 경로의 open-loop 도착률·dropped iterations, 다중 서버 인스턴스,
단일 UPSERT RETURNING 대안, 다른 DB 격리 수준, 운영 데이터 규모, 장시간 부하·DB 중단/재시작·deadlock 재시도.
운영 지연 목표와 트래픽이 없어 임의의 합격 TPS는 정하지 않았다.

## 재현 및 원시 근거

Docker(cgroup v2), JDK 21, Python 3, 기준 커밋을 읽을 수 있는 Git 체크아웃이 필요하다.
운영 자격증명을 사용하지 않는다. 원본 작업 파일을 바꾸지 않고 임시 사본에서 실행한다.

```sh
./gradlew clean build
python3 scripts/inquiry-experiment.py --output /absolute/path/to/new-evidence-directory
# 수정본만 측정
./gradlew inquiryExperiment -PexperimentVariant=fixed -PexperimentOutput=/absolute/path/to/results
```

기본 `test`/CI에서는 `experiment` 태그를 제외한다. 긴 측정과 의도적 실패 대조군을 기본 회귀 검증에 섞지 않는다.

## 포트폴리오에 사용할 수 있는 설명

“비관적 락을 사용한 문의번호 생성에서 기존 행 갱신과 첫 행 생성 경합을 분리해 검증했다.
락 제거 대조군과 실제 DB 잠금 대기로 기존 락의 역할을 확인하고, 첫 행 생성 충돌을 별도로 처리했다.
로컬 반복 실험에서 수정본 24,000건의 응답·저장·번호 유일성을 검증했으며,
동시 요청 증가에 따른 잠금·연결 풀 대기도 측정해 남은 한계로 기록했다.”

이는 이번 AI 도구를 활용한 개선·검증 기록이다. 과거 최초 개발 당시 수행한 실험이나 운영 성과로 소급하지 않는다.

## 최종 검증 기록

`./gradlew clean build --no-daemon` 성공. 기본 회귀 테스트 13개(문의 12 + 전체 컨텍스트 1), 실패·오류·스킵 0. 실험용 테스트는 별도 task에서 실행했다. 운영 배포·병합은 수행하지 않았다.
