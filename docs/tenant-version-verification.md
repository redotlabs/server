# 고객사 격리·페이지 버전 설계 검증

검증일: 2026-10-14 (Asia/Seoul)
기준 소스: `e17a550856bed95ba74ba0cf32b91ee52ed7eccd` (`develop`).
목적: 기존 포트폴리오의 문의번호·고객사 격리·작성본/공개본 주장만 보강한다.
이번 변경은 테스트와 문서이며 운영 코드·스키마를 바꾸지 않는다.

## 환경과 재현

- Java 21, Spring Boot 전체 컨텍스트, MockMvc의 실제 보안 필터·컨트롤러·서비스·JPA 경로.
- `docs/runtime-images.json`에 고정한 PostgreSQL 17.11 linux/amd64 Testcontainer와 실제 Flyway 마이그레이션.
- 독립적인 합성 고객사 A/B, 등록된 도메인, 고객사별 CMS OWNER를 테스트 DB에 준비한다. 정상 로그인 API가 발급한 쿠키를 사용하며 토큰을 임의 생성하지 않는다.
- 테스트 메서드 전체를 롤백 트랜잭션으로 감싸지 않는다. JDBC 검증은 서비스 커밋·롤백 뒤 실제 저장값을 조회한다.
- 초기화 SQL은 해당 테스트의 폐기용 컨테이너에만 실행한다. 홈서버 데이터는 생성·수정·삭제하지 않았다.
- MockMvc는 실제 네트워크 HTTP/Ingress/브라우저 테스트가 아니다. 실서버 고객사 격리·버전 검증, 부하·처리량 측정 결과로 표현하지 않는다.

```sh
./gradlew test --tests redot.redot_server.TenantAndVersionContractTest
./gradlew test
```

## DB 설계 평가 — 포트폴리오에 살릴 수 있는 이유

**판단: 현재 사이트 빌더의 버전별 페이지 구성을 보존하는 모델로 타당하며, 단순 상태 필드보다 강한 설계 사례다. 다만 아래 전제와 한계를 함께 설명해야 한다.**

| 설계 요소 | 코드·DB 근거 | 의미 |
|---|---|---|
| 내용/구성 분리 | `AppPage`, `AppVersion`, `AppVersionPage` | 버전은 페이지 집합의 스냅샷이고, 변경 없는 페이지는 여러 버전에서 참조 가능 |
| 변경 시 새 페이지 | `CMSSitePageService.addedPages/retainedPages` | 현재 생성 경로는 과거 콘텐츠를 덮어쓰지 않음. 공유 콘텐츠 행 수정 API는 확인되지 않음 |
| 작성·공개 분리 | `SitePageService.getSitePages` | PUBLISHED 구성만 공개 조회. DRAFT·PREVIOUS의 같은 경로는 노출되지 않음 |
| 최대 한 공개본 | V3 `uk_app_versions_published_per_app` | 상태가 PUBLISHED인 행에만 고객사별 유니크 적용. DRAFT/PREVIOUS는 여러 개 가능 |
| 버전 내 경로 유일성 | V3 `uk_app_version_page_path` + 서비스 중복 검사 | 한 버전에서 같은 경로에 둘 이상의 페이지가 대응하지 않음 |
| 전환 원자성 | `createAppVersion`의 트랜잭션 | 기존 상태 변경·신규 페이지·연결 저장 중 실패하면 기존 공개본이 유지됨 |

페이지 2개로 구성된 공개본에서 한 페이지만 변경한 예시를 실제 테스트했다. 새 버전은 기존 페이지 1개를 공유하고 새 페이지 1개를 저장하여 콘텐츠 행은 총 3개였다. 이는 **행 재사용 검증**이며 일반적인 저장 공간 절감률이나 성능 실측이 아니다.

### 정확히 설명해야 할 상태 의미

- `DRAFT`: 작성본 스냅샷. 현재 API에는 기존 DRAFT 행을 수정·승격하는 작업이 없다.
- `PUBLISHED`: 새 게시 요청으로 생성하는 현재 공개 구성. 내부적으로 DRAFT 상태로 생성 후 같은 트랜잭션에서 공개 상태로 바꾼다.
- `PREVIOUS`: 과거에 공개했던 버전들. 직전 버전 하나만 의미하지 않는다.
- `retained`로 작성본/이전 버전의 페이지를 선택해 새 버전을 만들 수 있지만, 전용 “버전 복원 API”와 동일하다고 주장하지 않는다.

### 한계와 향후 변경 시 주의점

1. **공유 페이지의 불변성은 현재 서비스 구현 규칙이다.** DB는 UPDATE 자체를 금지하지 않는다. 향후 페이지 수정 API가 기존 행을 덮어쓰면 과거 버전도 바뀐다. 변경 시 새 행을 만드는 규칙을 유지해야 한다.
2. **고객사 일치는 서비스에서 검사한다.** 연결 테이블의 두 FK만으로 버전과 페이지의 고객사 동일성이 보장되지는 않는다. 현재 retained API는 다른 고객사 페이지를 거절하며 이 경로를 검증했다. 직접 SQL·다른 쓰기 경로까지 DB가 막는다고 표현하지 않는다.
3. **`path`가 콘텐츠와 연결 행에 중복 저장된다.** 유니크 제약은 연결 행의 path, 조회·응답은 AppPage.path를 사용한다. 현재 생성 경로에서는 동일 값을 복사하지만, 향후 경로 수정 시 둘이 어긋나지 않는 설계가 필요하다. 버전별 경로 변경을 도입한다면 어느 쪽이 경로의 원본인지 먼저 정해야 한다.
4. **페이지 삭제가 과거 구성을 바꿀 수 있다.** V3의 페이지 FK는 ON DELETE CASCADE이므로 페이지를 직접 삭제하면 연결도 사라진다. 현재 페이지 삭제 API는 확인되지 않았다. 이력 정리는 참조 중인 페이지를 보존하는 정책이 필요하며, 현재 이력 불변성이 DB 전체에서 보장된다고 주장하지 않는다.
5. **동시 게시의 사용자 경험은 별도다.** 부분 유니크 제약은 공개본 중복을 막지만 두 편집자의 게시를 어떤 순서로 수락·거절할지는 정의하지 않는다. 현재 게시에는 명시적 버전 비교·고객사별 직렬화가 없다. 충돌 시 예외가 save 이후 flush에서 발생할 가능성도 있어 현재 save의 catch만으로 일관된 응답을 보장한다고 주장하지 않는다. 이번에는 동시 게시·충돌 응답 테스트를 수행하지 않았다.
6. **자동 정리·복구·페이지 수 제한은 이 검증의 결론이 아니다.** 이력 보존량, 전용 롤백, 실제 클라이언트 편집 흐름·복수 HTTP 조회의 같은 버전 고정 여부는 추가 요구사항으로 남긴다.

위 한계가 현재 테스트한 생성·조회·게시 원자성 계약을 무효화하지는 않는다. 요구사항 없이 버전 시스템 전체를 교체하기보다, 현재의 스냅샷·재사용 설계를 정확하게 설명하는 편이 적절하다.

## 고객사 격리 문구의 범위

`X-App-Subdomain`은 고객사를 선택하는 입력이며 권한 증명이 아니다. 등록 도메인으로 고객사를 찾고 CMS JWT의 `redot_app_id`와 비교한다. `@CurrentRedotApp`은 컨트롤러 인자 추출을 공통화하지만 서비스에는 고객사 ID를 계속 전달한다.

이번 테스트는 문의·페이지/버전 경로를 검증한다. 모든 CMS API, 관리자 권한 분리, 토큰 회수, CSRF 정책 등을 포괄하는 보안 감사 결과로 쓰지 않는다. 공개 사이트 API는 고객사에 해당하는 PUBLISHED 내용을 인증 없이 반환하는 것이 의도된 동작이다.
