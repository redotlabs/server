# 문의번호 첫 날짜 동시성 개선

검증일: 2026-10-14. 기준 커밋: `c373b2053b7f15c684ee8ffae2ba1665e63acf2d`.
작업 브랜치: `codex/inquiry-concurrency`. 로컬 변경 및 검증 결과이며 배포 결과가 아니다.

## 문제 재현

기존 코드는 날짜 행을 잠금 조회한 뒤, 행이 없으면 INSERT한다. 없는 행에 대한 조회 잠금은
동시에 INSERT하는 요청들을 직렬화하지 않는다. PostgreSQL의 날짜 UNIQUE 제약 위반을
같은 트랜잭션 안에서 잡고 재조회하는 방식으로는 정상 요청의 성공을 보장하지 못했다.

Java 21, 실제 Spring 서비스·JPA·Flyway 마이그레이션, 일회성 PostgreSQL 16 컨테이너로
재현했다. DB 연결 풀은 16개다. 가상 스레드 요청들을 시작 배리어에서 동시에 해제했다.
100개 요청은 100개 DB 트랜잭션이 동시에 실행된다는 뜻이 아니며 연결 풀 대기를 포함한다.
고객사 2개에 번갈아 요청했으므로 날짜 순번의 전역 유일성도 함께 검사한다.

| 초기 상태 | 요청 수 | 수정 전 성공 / 실패 | 수정 후 성공 / 실패 | 수정 후 저장 / 고유 번호 |
|---|---:|---:|---:|---:|
| 날짜 행 없음 | 2 | 1 / 1 | 2 / 0 | 2 / 2 |
| 날짜 행 없음 | 10 | 1 / 9 | 10 / 0 | 10 / 10 |
| 날짜 행 없음 | 100 | 85 / 15 | 100 / 0 | 100 / 100 |
| 기존 순번 40 | 2 | 2 / 0 | 2 / 0 | 2 / 2 |
| 기존 순번 40 | 10 | 10 / 0 | 10 / 0 | 10 / 10 |
| 기존 순번 40 | 100 | 100 / 0 | 100 / 0 | 100 / 100 |

단일 로컬 실행의 관측값이다. 수정 전 실패 수는 스케줄링에 따라 달라진다.
수정 전에는 시스템 날짜, 수정 후에는 고정 Clock으로 날짜를 제어했다.
성능 개선율·TPS·운영 성공률을 측정한 표가 아니다.

## 결정과 구현

1. `INSERT ... ON CONFLICT (inquiry_date) DO NOTHING`으로 날짜 행을 초기화한다.
   다른 요청이 먼저 생성 중이면 그 트랜잭션의 결과를 기다리고, 유니크 위반으로 현재
   트랜잭션을 실패시키지 않는다.
2. 기존 `PESSIMISTIC_WRITE` 조회 후 순번을 증가시킨다.
3. 일일 상한 99,999와 전역 날짜별 번호 형식 `INQyyyyMMddNNNNN`을 유지한다.
4. 문의 저장과 순번 변경은 같은 트랜잭션에 남긴다. 저장 실패 시 처음 생성한 날짜 행과
   기존 순번의 증가 모두 롤백된다. 별도 트랜잭션으로 번호만 먼저 커밋하지 않는다.
5. `Clock`을 주입하되 운영은 `Clock.systemDefaultZone()`을 사용해 기존 서버 시간대 기준을
   유지한다. 테스트에서만 Asia/Seoul 고정 Clock으로 자정 경계를 제어한다.

현재 PostgreSQL 기본 READ COMMITTED 환경에서 검증했다. 격리 수준을 바꾸거나 모든 호출을
다른 트랜잭션 범위로 묶는 경우에는 다시 검증해야 한다.

### 대안과 한계

- 충돌 예외를 잡아 같은 트랜잭션에서 재조회: 실제 실패가 재현되어 제거했다.
- 실패한 전체 트랜잭션 재시도: 가능하지만 문의 저장까지 재시도 범위·멱등성을 설계해야 한다.
- 증가까지 단일 UPSERT RETURNING: 비교 후보로 남겼다. 이번에는 기존 JPA 잠금·변경 감지와
  상한 검사를 유지하는 작은 수정으로 정합성 문제부터 해결했다. 대안의 우월성을 실측하지 않았다.
- Redis 채번: 별도 저장소와 DB 커밋 사이 정합성 문제가 추가되므로 도입하지 않았다.

기존 행에도 초기화 INSERT가 한 번 추가된다. 날짜별 전역 행 잠금과 DB 연결 풀 대기는
여전히 남아 있다. 최대 처리량 개선을 주장하지 않는다. PostgreSQL 고유 문법을 사용하지만
프로젝트 기존 DB도 PostgreSQL이다. 추가 스키마 마이그레이션은 없다.

## 회귀 검증

Docker와 JDK 21이 준비된 환경에서 다음을 실행한다.

```sh
./gradlew test --tests '*InquiryConcurrencyTest'
./gradlew clean build
```

- 신규 날짜·기존 날짜 각각 2/10/100 요청: 성공 수, 저장 수, 고유 번호 수, 최종 순번 검사.
- 서울 자정 직전과 직후: 날짜 변경 및 새 날짜의 00001부터 시작.
- 99,999번 성공과 다음 요청 거절: 잘못된 번호·문의가 저장되지 않음.
- 문의 저장 제약 위반: 신규 날짜 행·기존 순번 모두 롤백, 다음 정상 요청에서 번호 재사용.
- 기존 전체 컨텍스트 테스트: 일회성 PostgreSQL과 테스트용 값으로 기동.

`clean build` 최종 결과는 [확장 실험 보고서](inquiry-experiment-results.md)에 기록한다. 최초 실행은
11개 테스트(문의 10개 + 컨텍스트 1개)가 통과했고, 이후 잠금 대기·상한 경쟁 테스트를 추가했다.
문의 테스트와
컨텍스트 기동 테스트를 함께 실행한다. 테스트 전용 설정에는 운영 자격증명이 없으며 SMTP·Redis 주소는
로컬 닫힌 포트다. 컨텍스트 기동 성공은 Redis/메일/OAuth/S3 연동 성공을 뜻하지 않는다.

PR 테스트 워크플로를 추가하고 두 배포 워크플로에서 `-x test`를 제거했다.
호스팅 CI 결과는 PR의 체크에서 확인한다. 브랜치 보호 필수 체크 설정 변경, 병합·배포는 수행하지 않았다.

### HTTP 전체 경로와 대안 비교

먼저 테스트 전용 HTTP 서버와 합성 고객사·인증 데이터를 준비한다. 운영에 부하를 보내지 않는다.
같은 DB 버전·CPU/메모리·연결 풀·데이터 크기를 고정하고 기존 잠금 방식과 단일 UPSERT 후보를
각각 같은 조건에서 비교한다. 워밍업 이후 고정 도착률을 단계적으로 증가시키며 다음을 저장한다.

- HTTP 성공·실패·타임아웃·부하 도구의 미실행 요청 수를 별도 집계.
- p50/p95/p99 응답 시간과 완료 처리량, DB CPU·잠금 대기·Hikari 활성/대기 연결.
- 테스트 종료 후 요청 식별자별 실제 저장 여부, 번호 중복 0건, 정상 응답과 커밋 일치 여부.
- 신규 날짜 경합과 기존 날짜 지속 부하를 분리하고 반복 실행의 원시 결과 보존.

지연 목표와 운영 트래픽은 아직 확인되지 않았으므로 합격 TPS·임의 개선율은 정하지 않는다.
다음 Redot 과제는 고객사 격리 회귀 테스트와 상담 알림 트랜잭션 분리이며, 이번 변경에는 포함하지 않았다.
