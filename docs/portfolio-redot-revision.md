## Redot 1/2 — 페이지 내용과 버전 구성을 분리해 작성 중인 변경이 공개본에 섞이지 않게 했습니다

웹사이트 빌더와 CMS를 제공하는 B2B SaaS | 2025.07–2026.02 | 5인 팀, 백엔드 전담

### 01 페이지를 재사용하는 버전 스냅샷 설계

**문제**
편집 내용을 현재 공개 중인 페이지에 직접 반영하면 작성 중인 변경이 외부에 노출됩니다. 반대로 버전을 만들 때마다 모든 페이지 내용을 복제하면 바뀌지 않은 내용까지 중복 저장하게 됩니다.

**설계와 구현**
페이지 내용(`AppPage`), 버전의 상태(`AppVersion`), 버전별 페이지 구성(`AppVersionPage`)을 분리했습니다. 변경한 페이지는 새 행으로 저장하고, 유지할 페이지는 기존 행을 참조해 각 버전의 구성을 보존합니다.

작성본은 `DRAFT`로 저장합니다. 게시 요청은 새 버전을 만들고, 기존 공개본을 `PREVIOUS`로 전환하며 새 버전을 `PUBLISHED`로 지정합니다. 페이지 구성 저장과 상태 변경을 하나의 트랜잭션으로 묶었으며, 공개 API는 현재 `PUBLISHED` 버전에 연결된 페이지만 조회합니다.

DB의 부분 유니크 인덱스로 고객사별 공개본을 최대 하나로 제한하고, 버전 내 동일 경로 중복도 유니크 제약으로 막았습니다.

**2026.10 후속 검증**
실제 PostgreSQL을 사용하는 통합 테스트로 작성본 비공개, 게시 시 전체 페이지 구성 전환, 이전 내용 보존, 변경 없는 페이지 재사용을 확인했습니다. 중복 경로·없는 페이지·다른 고객사 페이지를 포함한 게시 요청이 실패하면 기존 공개본과 저장 건수가 유지되는지도 검증했습니다.

**설계에서 배운 점**
콘텐츠와 버전 구성을 나누면 공개 이력과 페이지 재사용을 함께 관리할 수 있습니다. 다만 공유한 페이지는 이후에도 수정하지 않는 규칙이 필요하며, 과거 버전 정리는 참조 관계를 고려해야 합니다.

도식 교체 지침: 기존 `DRAFT → PUBLISHED → PREVIOUS` 직선 그림을 “DRAFT 별도 저장 / 게시 요청으로 새 PUBLISHED 생성 / 기존 PUBLISHED는 PREVIOUS 전환”으로 바꾼다. 현재 API는 기존 DRAFT 행을 직접 승격하지 않는다. 여러 과거 공개본이 PREVIOUS로 남을 수 있다.

### 02 고객사 식별과 데이터 소속 확인

**문제**
같은 API를 사용하는 고객사 사이에서 요청의 고객사, 인증 토큰의 고객사, 조회·변경 대상 데이터의 고객사가 어긋나는 접근을 차단해야 했습니다.

**설계와 구현**
`X-App-Subdomain` 헤더를 등록된 도메인 정보와 대조해 요청의 고객사를 식별하고 요청 컨텍스트에 보관했습니다. CMS 인증 단계에서는 JWT의 고객사와 이를 비교합니다. 컨트롤러의 고객사 식별자 추출은 공통화하되, 서비스에는 식별자를 명시적으로 전달합니다.

문의 조회·상태 변경은 고객사와 문의 ID를 함께 조건으로 사용하고, 버전에 기존 페이지를 포함할 때는 페이지 소유 고객사를 확인합니다. 공개 사이트는 인증 없이 현재 고객사의 공개본을 조회합니다.

**2026.10 후속 검증**
A·B 고객사의 정상 로그인 쿠키로 문의 목록·상세·상태 변경, 버전 목록, 페이지 조회·재사용을 검증했습니다. 고객사와 토큰이 다른 요청 및 다른 고객사 데이터 접근이 거절되고, 실패한 요청이 저장 상태를 바꾸지 않는 것을 확인했습니다.

도식 교체 지침: “기능마다 고객사 정보를 다시 넘기지 않음”을 “공통 컨텍스트·인자 해석기로 고객사 추출 중복 제거”로 바꾼다. 헤더 자체가 권한을 증명하거나 모든 저장 경로가 자동으로 격리된다고 표현하지 않는다.

## Redot 2/2 — 기존 순번 행의 락을 유지하면서 첫 문의의 날짜 행 생성 경합을 해결했습니다

문의 접수 기능 | 날짜별 문의번호 `INQ + 날짜 + 5자리 순번` | 2026.10 후속 개선·검증

**문제**
기존 비관적 락은 이미 존재하는 날짜별 순번 행의 갱신을 직렬화했습니다. 하지만 당일 첫 문의가 동시에 들어오면 잠글 행이 없어 여러 요청이 같은 날짜 행을 만들려 했고, 유니크 제약 충돌로 정상 요청이 실패했습니다.

**해결과 선택 근거**
`INSERT … ON CONFLICT DO NOTHING`으로 날짜 행을 먼저 준비한 뒤, 기존 비관적 락으로 순번을 증가시키도록 변경했습니다. 문의 저장과 채번은 같은 DB 트랜잭션에 두어 저장 실패 시 날짜 행 생성 또는 순번 증가도 롤백되게 했습니다.

기존 잠금·상한 검사 구조를 유지하면서 첫 행 생성 경합만 해결하는 방법을 선택했습니다. 낙관적 락의 전체 트랜잭션 재시도나 Redis와 DB 사이의 정합성 처리를 추가하지 않았습니다. 다른 방식보다 성능이 우수하다는 주장은 하지 않습니다.

**검증**
실제 PostgreSQL에서 신규·기존 날짜 각각 동시 2·10·100개 요청을 검증하고, 기존 행의 잠금 대기, 자정 경계, 일일 상한, 저장 실패 시 롤백을 확인했습니다. 이후 홈서버의 실제 HTTP 경로에서 정상 1건·동시 2건·동시 10건, 총 13건의 응답·조회·DB 저장값과 고유 번호가 일치했습니다.

**배운 점**
이미 존재하는 행의 갱신과 처음 행을 만드는 경합은 별도로 검증해야 합니다. 유니크 제약은 중복 저장을 막지만, 충돌한 정상 요청의 성공까지 보장하지는 않습니다.

검증 범위 주석: 로컬 동시성 실험과 배포 후 HTTP 13건은 서로 다른 실험이다. HTTP 검증은 최대 처리량·장시간 부하·첫 행 경합 강제 재현을 의미하지 않는다. 신규 고객사·버전 테스트도 로컬 MockMvc+PostgreSQL 결과이며 홈서버 실측이 아니다.

## 사용하지 않을 표현

- “고객사 식별자를 서비스 인자로 전달하지 않는다.”
- “모든 고객사 데이터가 DB 수준에서 완전히 격리된다.”
- “기존 DRAFT 버전을 그대로 PUBLISHED로 승격한다.”
- “PREVIOUS는 직전 공개본 하나만 남는다.”
- “과거 버전 복원 기능 / 동시 게시 충돌 처리까지 완성했다.”
- “저장 공간을 N% 절감 / 처리량 N배 향상 / 대규모 운영 안정성 입증.”
